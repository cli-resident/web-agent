# Материал для защиты проекта WEB-AGENT

## Введение

WEB-AGENT — это кроссплатформенный фоновый сервис для удаленного выполнения задач с фокусом на сетевую диагностику endpoint-ов и автоматическую генерацию человеко-читаемого summary через внешний AI API.  
Архитектурно проект построен как модульное C++17-приложение с разделением ответственности между конфигурацией, сетевым слоем, оркестратором агента, обработчиками задач и логированием.

Ключевая прикладная ценность проекта:
- централизованная проверка доступности сервисов;
- единый формат отчета для машины (`JSON`) и человека (`summary.txt`);
- возможность встроить агента в распределенную инфраструктуру без GUI и ручных действий.

---

## 1. Общая архитектура и поток работы

При запуске `web_agent` выполняется следующий жизненный цикл:

1. `main.cpp` разбирает аргументы запуска и загружает конфигурацию.
2. Инициализируется логгер (`Logger`) для трассировки всего процесса.
3. Создается `Agent`, внутри которого инициализируются `HttpClient` и `TaskHandler`.
4. Агент регистрируется на сервере (если отсутствует `access_code`).
5. Запускается цикл опроса сервера задач (`wa_task`).
6. Полученные задачи передаются в `TaskHandler::process`.
7. По результатам выполнения вызывается `wa_result` с итогом и файлами артефактов.

Таким образом, `Agent` — это orchestration-слой, а фактическая бизнес-логика задач сосредоточена в `TaskHandler`.

## 2. Реализация по файлам

## 2.1 `src/main.cpp` — точка входа и управление запуском

В `main.cpp` решаются задачи:
- обработка CLI-аргументов (`--config`, `--help`, `--version`);
- создание и загрузка `Config`;
- запуск `Logger::init`;
- создание экземпляра `Agent`;
- вызов `agent.init()` и `agent.run()`.

Почему это важно:
- `main.cpp` остается компактным и не перегружен бизнес-логикой;
- модульность упрощает тестирование и поддержку.

---

## 2.2 `src/config.cpp` / `include/config.h` — конфигурация

Модуль конфигурации отвечает за:
- чтение `config.json`;
- валидацию обязательных параметров (`uid`, `server_url`);
- хранение runtime-параметров (`poll_interval_sec`, `result_directory`, retry и др.);
- сохранение обновленного `access_code` после успешной регистрации.

Практическая роль:
- конфиг выступает как контракт между оператором и агентом;
- важные параметры выведены из кода, что делает поведение агента управляемым без пересборки.

---

## 2.3 `src/logger.cpp` / `include/logger.h` — логирование

Логгер построен на `spdlog` и обеспечивает:
- вывод в stdout;
- запись в файл с ротацией;
- уровни логирования (debug/info/warn/error);
- потокобезопасность при конкурентной записи.

Почему это критично:
- фоновый агент без GUI требует надежной наблюдаемости;
- логи служат источником диагностики сетевых и бизнес-ошибок;
- ротация защищает систему от бесконтрольного роста файлов.

---

## 2.4 `src/http_client.cpp` / `include/http_client.h` — HTTP слой

`HttpClient` инкапсулирует сетевое взаимодействие с сервером:
- `registerAgent()` -> `POST /wa_reg`;
- `requestTask()` -> `POST /wa_task`;
- `sendResult()` -> `POST /wa_result` (multipart).

Технические детали:
- используется `cpr` как обертка над libcurl;
- раздельные таймауты connect/request/upload;
- проверка HTTP-статусов и ошибок транспорта;
- JSON-парсинг ответов через `nlohmann::json`;
- поддержка прикрепления файлов к результату.

Преимущества такого решения:
- сетевые детали изолированы от orchestration/бизнес-логики;
- легче тестировать и модернизировать API-контракт.

---

## 2.5 `src/agent.cpp` / `include/agent.h` — оркестратор

`Agent` отвечает за управление жизненным циклом:
- регистрация и получение токена доступа;
- запуск и остановка цикла опроса;
- обработка ошибок запроса задач;
- делегирование каждой задачи в `TaskHandler`.

Цикл опроса:
- агент периодически вызывает `requestTask()`;
- при `WAIT` продолжает polling;
- при задаче (`code==1`) запускает обработку.

Роль модуля:
- связать конфигурацию, сеть и обработчики в единый управляемый процесс.

---

## 2.6 `src/task_handler.cpp` / `include/task_handler.h` — задачи и бизнес-логика

`TaskHandler` — главный функциональный модуль проекта.

Маршрутизация:
- `TIMEOUT` -> меняет интервал опроса и сохраняет конфиг;
- `CONF` -> пока заглушка;
- `FILE` -> сохраняет payload в `test_payload.json`;
- `TASK/EXEC/CMD` -> выполняет сетевую диагностику endpoint-ов.

### Что происходит в сетевой задаче

1. Парсинг `options` как JSON.
2. Чтение массива `targets`.
3. Для каждой цели — HTTP GET probe (`probeTarget`).
4. Сбор метрик:
- доступность (`success`);
- HTTP status code;
- latency;
- размер ответа (`bytes`);
- текст ошибки.
5. Формирование отчета `netdiag_<session_id>.json`.
6. Генерация текстового summary через AI.
7. Сохранение summary в `netdiag_<session_id>_summary.txt`.
8. Отправка результата и файлов на сервер.

Почему это сильная часть проекта:
- в одном pipeline объединены мониторинг, аналитика и доставка результата;
- есть machine-readable и human-readable представления одной диагностики.

---

## 2.7 Работа с AI API (Mistral)

Интеграция реализована в `buildAiSummary`.

Схема:
- формируется JSON payload для chat completion;
- передается system prompt, задающий строгий формат ответа;
- user content — полный JSON-отчет;
- ответ парсится из `choices[0].message.content`.

Отказоустойчивость:
- при сетевой ошибке, ошибке статуса или некорректном формате ответа используется `buildFallbackSummary`;
- fallback формирует техническую сводку без участия AI.

Практический смысл:
- даже при недоступности внешнего AI агент не теряет функциональность и возвращает полезный результат.

Замечание по безопасности:
- в текущем виде API key задан константой в коде;
- для production ключ должен храниться в секрете окружения/конфиге, а не в исходниках.

## 3. Форматы данных и артефактов

Входная задача netdiag:
- `targets[]` с полями `url` и опциональным `timeout_sec`;
- общий `timeout_sec`.

Выходные артефакты:
- `results/netdiag_<session_id>.json` — подробный технический отчет;
- `results/netdiag_<session_id>_summary.txt` — итоговая сводка.

В серверный результат отправляются:
- `result_code`;
- `message` (обычно AI/fallback summary);
- список файлов-артефактов.

---

## 4. Тестирование и качество

В проекте присутствуют тесты инфраструктуры и модулей (директория `tests/`), а также CI-пайплайн в GitHub Actions.

Подход к качеству:
- модульная структура упрощает изолированное тестирование;
- централизованное логирование ускоряет отладку;
- fallback-логика снижает риск отказа при внешних зависимостях.

Рекомендуемое развитие тестов:
- unit-тесты `TaskHandler` для различных `task_code`;
- мокирование HTTP-вызовов и AI API;
- интеграционные сценарии полного цикла `wa_task -> wa_result`.

---

## 5. Ограничения текущей версии

- `CONF` пока не реализован полноценно;
- `EXEC/CMD` в текущей реализации сведены к netdiag-сценарию;
- секрет AI API хранится в коде;
- требуется дальнейшее расширение автоматизированных тестов.

Эти ограничения осознаны и могут быть устранены в следующих итерациях без ломки архитектуры.

---

## 6. Итог для защиты

Проект реализует рабочий агент удаленной диагностики с понятной модульной архитектурой:
- конфигурируемый запуск;
- устойчивое логирование;
- надежный HTTP-обмен с сервером;
- детальная обработка задач;
- интеграция AI-summary с fallback;
- возврат результатов в виде файлов и сообщения.

С инженерной точки зрения система демонстрирует:
- разделение ответственности;
- эксплуатационную наблюдаемость;
- отказоустойчивое поведение при частичных сбоях;
- готовность к эволюции под production-требования.
